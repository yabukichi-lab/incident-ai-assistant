# 設備トラブル対応記録 AI アシスタント

設備トラブル記録を扱う小規模な業務Webアプリケーションを、短い開発サイクルで段階的に成長させる学習プロジェクトです。

最初は通常のCRUDアプリケーションとして開始し、LLMによる要約、RAG、読み取り専用エージェント、人間承認付きDB更新まで拡張します。

このプロジェクトでは、完成コードを最初に一括生成することよりも、次の反復を重視します。

```text
小さく動かす
  ↓
処理の流れを確認する
  ↓
理由を理解する
  ↓
小さな変更を加える
  ↓
テストと記録を残す
```

## 1. プロジェクトの目的

### アプリケーションとしての目的

設備トラブル記録について、最終的に次の操作ができるWebアプリケーションを作ります。

1. トラブル記録を閲覧・登録・更新する
2. 条件やキーワードから記録を検索する
3. AIが記録を要約する
4. マニュアルや過去記録を根拠として質問に回答する
5. AIが読み取り用ツールを選択して実行する
6. AIがDB更新案を作成する
7. 人間が差分を確認し、承認した場合だけDBを更新する
8. 検索、回答、承認、更新の履歴を確認する

### 学習としての目的

- React、TypeScript、FastAPI、PostgreSQLをつないだWebアプリケーションの全体像を理解する
- HTTP、入力検証、DB、トランザクション、例外、テストの役割を理解する
- LLMを制御可能な外部依存としてアプリケーションに組み込む
- RAGを検索・コンテキスト構築・回答生成・評価に分解して理解する
- AIエージェントをツール選択、実行、状態遷移、安全制御に分解して理解する
- Codexに依存したまま終わらず、段階的に自分の判断範囲を広げる

## 2. データ方針

本プロジェクトは、学習専用の架空の設備トラブル対応システムとして構築します。

- 実在する会社、工場、部署、設備、製品、人物の情報は使用しない
- 実際の業務で使用しているトラブル履歴、マニュアル、文書、識別子、コード体系は使用しない
- 設備、エラーコード、トラブル履歴、マニュアル、利用者情報はすべて合成データとする
- 合成データは最初から大量に準備せず、各マイルストーンで必要になった分だけ追加する
- 最初は内容を把握できる少数の固定データを使い、件数が必要になった時点でseedスクリプトを追加する
- ランダム生成する場合はseedを固定し、同じ条件で再生成できるようにする
- 工学的な正確性の再現よりも、データ間の一貫性と学習目的への適合を優先する
- 詳細な設備マスターや文書内容は、該当マイルストーンの開始時に定義する

本プロジェクトに登場する設備、エラーコード、トラブル履歴、組織、人物、文書はすべて架空です。実在する企業、設備、業務との関係はありません。

## 3. 学習方針

### 実装を先に進める

基礎が固まっていない初期段階では、設計を白紙から考えることを必須にしません。Codexが提示する手順を基に実装し、まず動作確認まで到達します。

ただし、手順をそのまま消化するだけにはしません。各サイクルで最低限、次を行います。

- 実装前に「何が変わるか」を短く確認する
- 実装後に入力から出力までの処理経路を確認する
- 正常系だけでなく、異常系を1つ確認する
- 小さな仕様変更を1つ加える
- 分からない点を `docs/PROGRESS.md` に残す

### 全体は既存技術で作り、核心だけ小さく再実装する

Webサーバー、DBエンジン、認証、暗号などをゼロから作りません。一方で、学習価値が高い次の仕組みは、`labs/` で簡易版を作る場合があります。

- SQLの実行とトランザクション
- Repositoryの差し替え
- チャンキング
- cosine類似度とTop-k検索
- ハイブリッド検索
- LLMのFake実装
- ツール実行ループ
- 承認状態機械

### 未来の詳細を作り込みすぎない

全体方針は `docs/ROADMAP.md` に記載しますが、各マイルストーンの詳細なサイクルは、該当マイルストーンを開始するときにだけ作成します。

現在の詳細計画の参照先は `docs/PROGRESS.md` で確認します。各マイルストーンの詳細ファイルは、開始時に `docs/milestones/TEMPLATE.md` から作成します。

## 4. 技術構成

| 領域 | 採用技術 |
|---|---|
| バックエンド | Python / FastAPI / Pydantic |

| フロントエンド | TypeScript / React / Vite |
| DB | PostgreSQL |
| Pythonテスト | pytest |

ライブラリは必要になったマイルストーンで導入します。最初からすべてを追加しません。

## 6. ドキュメントの役割

| ファイル | 役割 | 更新タイミング |
|---|---|---|
| `README.md` | 長期的に変わりにくい目的と基本方針 | 方針自体が変わったとき |
| `AGENTS.md` | Codexの役割、進行方法、禁止事項 | Codexとの進め方を改善したとき |
| `docs/ROADMAP.md` | 全マイルストーンの成果と通過条件 | 大きな順序変更が必要なとき |
| `docs/SCHEDULE.md` | 全体期間、マイルストーン期間、週次目標 | 4週間ごと、またはマイルストーン完了時 |
| `docs/milestones/Mx.md` | 現在のマイルストーンの詳細サイクル | 開始時と各サイクル完了時 |
| `docs/PROGRESS.md` | 現在地、次の作業、直近の結果と参照先 | 承認済みの進捗更新時 |
| `docs/history/Mx.md` | 過去の作業・確認結果・判断 | 承認済みの履歴記録時 |
| `docs/learning/Mx.md` | 技術・実装の疑問と理解の変化 | 学習記録の運用に従い、承認済みの記録時 |

情報が食い違う場合、現在地と次の作業については `docs/PROGRESS.md` を正とします。

## 7. 開発セッションの進め方

1. Codexが `AGENTS.md` の規則に従い、`docs/PROGRESS.md`、Gitの変更状態、現在のマイルストーンの基本情報・スコープ・該当サイクルと関連コードを必要な範囲で確認する
2. Codexが現在のサイクルで行う次の1ステップを提示する
3. Codexが「なぜ今それを実装するのか」を説明する
4. 変更案と確認方法を提示し、承認済みの範囲で実装またはコマンド実行を行う
5. 期待結果と実際の結果を比較する
6. 正常系の確認後、異常系を最低1つ確認する
7. ユーザーが疑問点を質問する
8. 承認済みの範囲で、短い進捗要約、マイルストーンのチェック、必要な履歴・学習記録を更新する
9. 次回最初に行う作業を1つだけ明記して終了する

通常の再開では5文書を毎回全文読む必要はありません。概要・全体計画・過去の履歴は必要なときに該当箇所を参照します。質問・相談では質問に関係する情報を確認します。

## 8. サイクルの完了条件

各サイクルは、次を満たしたときに完了とします。

- ユーザーから見える動作、または確認可能な技術的結果がある
- 正常系が再現できる
- 代表的な異常系を最低1つ再現できる
- 自動テストまたは再現手順がある
- 入力から出力までの流れを説明できる
- Codexが生成・変更した主要コードの役割を説明できる
- 小さな変更を1つ加えても動作を維持できる
- `docs/PROGRESS.md` が更新されている

理解確認に答えられなくても、そこで進行を止めません。Codexが補足説明し、未理解事項として記録した上で次へ進みます。

## 9. 現在のスコープ

現在は **M0: 開発基盤とエンドツーエンド疎通** を開始します。

M0では次だけを扱います。

- FastAPIの起動
- PostgreSQLの起動
- FastAPIからPostgreSQLへの疎通
- Reactの起動
- ReactからFastAPIへの疎通
- 各境界での失敗確認

M0では、LLM、RAG、認証、エージェント、非同期ジョブ、PDF・Excel解析を導入しません。

## 10. Codexで開始するときの指示

新しいセッションでは、次の指示から開始します。

```text
AGENTS.mdの読み込み規則に従い、docs/PROGRESS.mdから現在地を確認してください。
現在のマイルストーンの基本情報・スコープ・該当サイクルと関連コードを必要な範囲で確認し、
次に行う1ステップの目的、理由、対象ファイル、変更内容、期待結果、確認方法を説明してください。
変更は承認済みの範囲で進め、今回不要な文書の全文読み込みや機能・ライブラリ追加は避けてください。
```

## 11. 最初の到達点

最初の到達点は、ブラウザ上で次を確認できる状態です。

```text
Frontend: OK
Backend: OK
Database: OK
```

この状態に到達してから、M1で設備トラブル記録の読み取り機能へ進みます。
