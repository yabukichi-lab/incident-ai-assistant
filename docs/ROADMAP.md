# 学習・開発ロードマップ

## 1. このドキュメントの役割

このファイルは、設備トラブル対応記録AIアシスタントを完成させるまでの全体像を示します。

ここには、各マイルストーンの次の情報だけを記載します。

- ユーザーから見える到達状態
- 学習目的
- 主な実装対象
- 簡易再実装する中核概念
- マイルストーンの通過条件
- 対象外

各マイルストーン内部の詳細なサイクルは、開始時に `docs/milestones/Mx.md` として作成します。未来の詳細サイクルは、このファイルには記載しません。

## 2. 開発原則

1. 1つのアプリケーションを段階的に育てる
2. ユーザーから見える小さな成果を先に作る
3. 動作確認後に内部構造を深掘りする
4. 1サイクルで主要概念を1つだけ追加する
5. 全体は既存技術で作り、中核概念だけ `labs/` で簡易再実装する
6. 評価結果や実際の問題がない機能は先回りして追加しない
7. 次のマイルストーンへ進む前に、現在の通過条件を確認する

## 3. データ戦略

本プロジェクトでは、実際の会社・設備・業務データを使用せず、すべて架空の合成データを使用します。

- 実在する会社、工場、部署、設備、製品、人物、文書、識別子を再現しない
- データは最初から大量に準備せず、各マイルストーンの目的に必要な分だけ追加する
- 最初は人が内容を把握できる固定データを使い、件数が必要になった時点で再現可能なseedスクリプトを追加する
- 工学的な正確性よりも、設備・エラーコード・履歴・マニュアル間の一貫性を優先する
- RAGや検索評価では、期待する検索文書と回答要素をあらかじめ定義する
- 個別の設備名、エラーコード、履歴、文書本文は、該当マイルストーン開始時にだけ具体化する

| マイルストーン | 合成データの方針 |
|---|---|
| M0 | 業務データを使用しない |
| M1 | 内容を確認できる固定トラブル記録を5〜10件用意する |
| M2 | 登録、更新、入力不正、対象なしを確認できるデータを追加する |
| M3 | 検索、ソート、ページングを確認できる30〜50件程度へ増やす |
| M4 | 要約結果を確認しやすい代表的な記録を使用する |
| M5 | 架空のMarkdown・テキスト文書を5〜10件作成する |
| M6 | 質問、期待文書、期待要素を持つ評価ケースを15〜20件作成する |
| M7 | 記録検索、詳細取得、文書検索を区別できる質問とデータを用意する |
| M8 | 承認、却下、競合、二重実行を再現できる更新対象を用意する |
| M9 | 複数ロール・部署の認可を確認する架空ユーザーを用意する |

件数は固定要件ではなく目安です。現在の学習目的を満たす最小量を優先します。

M8を学習プロジェクトとしての第一完成地点とします。M9は実務品質への拡張です。

# M0: 開発基盤とエンドツーエンド疎通

## ユーザーから見える到達状態

ブラウザで、フロントエンド、バックエンド、DBの状態を確認できる。

```text
Frontend: OK
Backend: OK
Database: OK
```

## 学習目的

- ブラウザ、React、FastAPI、PostgreSQLの境界を把握する
- HTTP通信とDB接続を区別する
- 障害が発生した場所を切り分ける基礎を作る
- プロジェクトを再起動可能な状態にする

## 主な実装対象

- FastAPIのhealth API
- PostgreSQLのDocker Compose構成
- FastAPIからPostgreSQLへの疎通確認
- Reactの状態表示画面
- ReactからFastAPIへのHTTP通信

## 簡易再実装・確認対象

- `curl`によるHTTP確認
- `psql`によるDB直接確認
- 各プロセスを停止したときの失敗差分

## 通過条件

- [ ] バックエンド単体でhealth APIを呼べる
- [ ] PostgreSQLへ接続できる
- [ ] DB停止時にバックエンドが異常を返す
- [ ] Reactからバックエンドの状態を表示できる
- [ ] フロント、バックエンド、DBの責務を説明できる
- [ ] READMEに起動・確認手順が反映されている

## 対象外

LLM、RAG、認証、CRUD、非同期DB、ジョブキュー、PDF・Excel解析。

## 学習モード

Level 1: Follow

詳細: `docs/milestones/M0.md`

# M4: LLMによる単機能

## ユーザーから見える到達状態

トラブル記録の詳細から、AIが概要、想定原因、確認事項、次の対応候補を構造化して生成する。

## 学習目的

- LLMをアプリケーション全体ではなく外部サービスとして扱う
- LLM固有コードと業務ロジックを分離する
- 構造化出力を検証する
- timeout、API障害、不正出力を安全に処理する

## 主な実装対象

- `LLMProvider` インターフェース
- Fake LLM
- 実LLM API接続
- Pydanticによる構造化出力
- エラー処理と呼び出し記録

## 簡易再実装・確認対象

- Fake LLMによる決定的テスト
- 不正JSON、不足項目、timeoutの再現

## 通過条件

- [ ] Fakeと実LLMを切り替えられる
- [ ] LLMなしで自動テストが通る
- [ ] 不正出力をそのまま表示・保存しない
- [ ] API障害でも通常機能が停止しない
- [ ] LLMがDBを直接更新しない
- [ ] LLM境界を説明できる

## 対象外

チャット、RAG、ツール実行、DB更新エージェント。

# 6. マイルストーン変更ルール

ロードマップは固定された契約ではありません。実装中に前提が変わった場合は変更できます。ただし、次のルールに従います。

- 現在のマイルストーン中は、受け入れ条件に直接必要でない機能を追加しない
- 追加案は `docs/PROGRESS.md` の保留事項へ記録する
- マイルストーン終了時に、追加・削除・順序変更を検討する
- 技術的な興味だけでロードマップを拡大しない
- 変更理由を記録する

# 7. 完成の定義

第一完成はM8です。

M8完了時には、次の一連の流れを実演できる状態を目指します。

```text
トラブル記録を登録する
  ↓
過去記録や文書を検索する
  ↓
AIが根拠付きで回答する
  ↓
AIが読み取りツールを選択する
  ↓
AIが更新案を作る
  ↓
利用者が差分を確認する
  ↓
承認後だけDBを更新する
  ↓
監査ログで変更を確認する
```
