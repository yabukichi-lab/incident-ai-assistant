## L-M0-004

- 日付: 2026-09-09
- 記録日: 2026-09-09
- サイクル／ステップ: M0-C1／リクエストからJSON応答までの処理経路の確認
- テーマ: UvicornとFastAPIの関係
- きっかけ: 処理経路の説明、関連質問、Uvicorn停止時の挙動についての本人の報告

### 学ぶこと・確かめたいこと

Uvicorn、FastAPI、自分で書く関数の役割を区別する。HTTP通信とPython内部の呼び出しの境界、接続失敗と404の違い、アプリ開発で実装する範囲を理解する。

### 当初の理解・疑問

本人は、UvicornとFastAPIが別々のサーバーとしてHTTP通信しているのか、なぜ両者が分かれているのかを質問した。また、開発時にUvicorn側にも処理を実装するのか、起動時の指定だけを扱うのかを確認した。

### 取り組んだこと

既存の `GET /health`、`health()`、起動コマンド `uv run uvicorn main:app --reload` を例に、通信とアプリケーション内部の処理を対応付けて説明した。
本人は、Uvicorn停止時にブラウザで「このサイトにアクセスできません」と表示されることを報告し、404との違いを自分の言葉で説明した。
Codexは公式ドキュメントを参照して回答した。今回の記録作業ではコード変更、サーバー起動、HTTP通信の再検証は行っていない。

### 質問と回答

以下の質問はこの会話の原文。誤字・表記も原文どおりに残し、回答は要約として記載する。

**質問1（原文）: Uvicornの役割**

> Uvicornとはなんですか？FastAPIとどんな関係があるか、解説してください。

回答（要約）:

UvicornはHTTP通信を受け付け、FastAPIで作ったアプリケーションを動かすサーバープログラム。FastAPIはURLに対応する処理の選択、入力検証、レスポンス作成を担当し、本人が書く `health()` などの関数がアプリ固有の処理を担当する。

具体例:

```text
ブラウザ／curl
  → HTTP通信 → Uvicorn
  → Python内部でFastAPIのappを呼ぶ
  → FastAPIがhealth()を呼ぶ
  → 辞書を返す
  → FastAPIがJSONの応答を作る
  → UvicornがHTTPレスポンスを送る
  → ブラウザ／curlが表示する
```

**質問2（原文）: 接続失敗と404の違い**

> uvicorn を停止した状態で/healthにアクセスすると、このサイトにアクセスできません。と返されます。これは、404のようにありません。というわけではなく、そもそもアクセスできないためあるかどうかすらわからないという、404野さらに前段階で止まっているという理解であっていますか？

回答（要約）:

その理解で合っている。停止時は接続する段階で失敗し、HTTPレスポンスを受け取れていない。「このサイトにアクセスできません」はブラウザ自身のメッセージ。一方、404はサーバーに接続でき、FastAPIがURLを調べた結果として返すHTTPレスポンス。接続できなければ `/health` の存在を調べる段階まで進めない。

**質問3（原文）: 同じサーバーで動くのか、分離する意味は何か**

> Uvicorn と FastAPIは同じサーバーで稼働している、という理解であっていますか？ブラウザからUvicorn(サーバー)にHTTPリクエストを行い、Uvicorn(サーバー)からFastAPI(サーバー)に通信をしているのでしょうか？
> UvicornとFastAPIが分かれていることの意味がわかりません。

回答（要約）:

今の構成では、UvicornとFastAPIで作ったアプリは同じPC上の同じサーバープロセス内で動く。ブラウザとUvicornの間はHTTP通信だが、UvicornからFastAPIへはPython内部で呼び出し、別のHTTP通信は行わない。両者の呼び出し方とデータの受け渡しを定める取り決めがASGI。

「サーバー」という言葉がコンピューターとサーバープログラムの両方を指すことを整理した。通信を扱う仕事をUvicorn、URLの振り分けなどをFastAPIに分けることで、それぞれの仕組みを再利用できる。ASGIに対応する別のサーバープログラムでアプリを動かすこともできる。

補足として、`--reload` のログに出る `reloader process` はファイル監視用の別プロセスであり、Uvicorn用とFastAPI用に分かれたものではないと説明した。最初の説明では「同じプログラム内部で動く」ことを十分に伝えていなかったため、この質問への回答で補足した。

**質問4（原文）: 開発時にUvicornをどこまで扱うか**

> FastAPIで開発を行うときは、当然FastAPI側の開発を行い、Uvicorn側に何かを実装するということはないのでしょうか？uv run コマンドで、どのファイルを読ませるかくらいでしか触らないのでしょうか？

回答（要約）:

通常はFastAPIを使ったアプリケーションコードを実装し、Uvicornは起動コマンドや設定を通して利用する。Uvicorn本体のコードを編集することは通常ない。読み込むアプリ以外にも、待ち受けアドレス、ポート、自動再読み込みなどを設定する。

```text
uv run   → プロジェクトの環境で、後ろのコマンドを実行する
uvicorn  → サーバープログラムを起動する
main:app → main.py内のappをUvicornに読み込ませる
--reload → Uvicornの自動再読み込みを有効にする
```

具体例として `uv run uvicorn main:app --reload --port 8001` を提示した。同じアプリのまま接続先ポートを変える設定例であり、変更を実行した記録はない。

### 得られた知識・気づき

- UvicornはHTTP通信、FastAPIはURLの振り分けなど、自作関数はアプリ固有の処理を担当する。
- 現在の構成ではUvicornとFastAPIの間に別のHTTP通信はなく、サーバープロセス内でASGIに従って呼び出す。
- 接続失敗はHTTP応答を受け取る前に起こり、404は接続後に返される応答である。
- uvは環境・依存関係の管理とコマンド実行を担当する。Uvicornとは別のツールであり、`main:app` を解釈してアプリを読み込むのはUvicorn。
- アプリ固有の機能は自分のコードに実装し、Uvicornは通信を受け付けるための設定を扱う。

### 理解の確認

- 確認状況: 接続失敗と404の違いは本人が説明。UvicornとFastAPIの役割分担は説明後に理解の表明あり。
- 本人の説明・確認結果: 質問2で、接続できなければURLの存在を確認する前段階で止まると説明した。停止時のブラウザ表示は本人の報告に基づく。
- 本人の理解の表明（原文）: 質問4への回答後に「理解しました。続きの作業を教えてください。」と返答した。
- 確認の限界: 上記の表明は記録するが、ASGI、同じプロセス内の呼び出し、全体の処理経路を本人が自分の言葉で説明できたとまでは判定しない。
